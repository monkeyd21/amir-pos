Technical Specification · Draft 1

An online store on the shop's own till

A public e-commerce site for Sabiha's Ethnic — children's ethnic wear, sizes 12 to 36 — sharing one database with the existing POS and ERP. The catalogue is the shop floor: the same stock room serves a website visitor and a walk-in customer at the same instant. Keeping those two channels honest with each other, not the shopfront, is what this document is mostly about.

1Scope & decisions

Four decisions were taken before this spec was written. Everything below follows from them.

IDDecisionChoiceRationale
D1Topology New workspace, same monorepo One Prisma schema, one migration history, one deploy. Offers, loyalty, GST and checkout are imported, not reimplemented or proxied.
D2Storefront stack Next.js App Router + Tailwind Retail discovery is organic search. Server-rendered product pages are indexable; a client-rendered SPA effectively is not.
D3Stock model Live shared stock, cart reservation One stock room, two channels selling from it simultaneously. A soft hold with expiry is what stops the site and the counter contradicting each other.
D4v1 scope Browse → pay → ship Fully transactional. Click-and-collect and WhatsApp ordering are additive, not blockers.
D6Catalogue Kids ethnic wear, sizes 12–36 Numeric Indian kidswear sizing mapped to ages 6 months to 16 years. The number does not explain itself to a parent, so age travels with it everywhere. See §3.4.

Out of scope for v1

Wishlist, reviews, guest checkout without OTP, multi-currency, abandoned-cart automation, click-and-collect, reverse-pickup returns, and any loyalty-tier-gated online pricing.

2Architecture

The storefront is a separate process with a separate domain, but not a separate database and not a separate source of truth. All pricing, tax, offer and loyalty logic stays in the Express backend and is called by the shop module directly — a Next.js route handler never computes a price.

Boundary rule

The storefront owns presentation and nothing else. Any money figure it renders came from the backend. This keeps a single implementation of the MRP → sale-price → offer → loyalty → GST chain, which is the part of the system most expensive to get subtly wrong in two places.

3Data model

The existing schema already anticipated this project in three places: SaleChannel.online exists, Sale.clientRef gives idempotent checkout, and BillSequence is documented as supporting a separate online bill prefix. What it does not have is any notion of an image, a customer login, a structured address, a cart that holds stock, or an order that is not yet a sale.

Migration discipline

Every column above is nullable or defaulted, and every new table is additive. No existing column changes type or nullability, so the POS can keep running against the same database throughout the build. Follow the reviewed-SQL practice already used for the payroll release (deploy/sql/).

3.3 Why an order is not a sale

In this system a Sale means something precise: money was taken, stock left the building, GST was recorded, loyalty accrued, the day's rollup moved. An online order that has been placed but not paid satisfies none of that.

So ShopOrder carries the lifecycle, and the Sale row is written exactly once, at payment confirmation, with channel: 'online'. A cancelled unpaid order leaves no trace in the books, and the accounting, reporting and P&L code needs no changes at all to stay correct.

3.4 Sizing

Sizes are numeric, 12 to 36, mapped to age. The number is roughly the chest in inches; the mapping is not obvious to a shopper, which is exactly why the shop hands out a size chart.

What this costs in code:

  • Size gains ageLabel, chestInches and lengthInches. The model today is { name, sortOrder, isActive } with nowhere to put an age. Every customer-facing surface renders the pair — 22 · 4 years — while the barcode label keeps printing the bare number.
  • The real grid must be seeded. backend/prisma/seed.ts currently carries demo sizes (Levi's 28–36, Nike S–XXL). Thirteen real sizes replace them before any catalogue work starts.
  • Age is a browse axis, not a footnote. Parents arrive knowing an age, not a size, so it belongs in navigation and in the listing filters beside category.
  • Thirteen variants per style adds up. A 300-style catalogue is roughly 3,900 variants, which makes the listing availability query (§4) the hottest read on the site. A card showing "in stock" means some size is available — it must never imply the shopper's size is.
Scope pressure

In kidswear the commonest reason a parcel comes back is the wrong size, not a faulty garment. Reverse logistics currently sits in Phase 9, which is probably too late — a same-product, different-size exchange is likely the main support flow from day one. The machinery exists already (Return, ReturnItem, pos/exchange-policy.ts); what is missing is a customer-facing path into it.

4Availability & reservations

The site and the counter draw on the same stock. A cashier can scan the last of something in the same second a shopper online is paying for it. Stock is thin today — the schema notes minStockLevel defaults to 0 because most articles are currently single-piece — so collisions are frequent now and merely occasional once buying moves to depth. This section is the answer either way.

The policy, in one line

An in-store scan beats an unpaid web hold. A paid web order beats an in-store scan. Settled money wins; unsettled intent loses. Every rule below is a mechanical consequence of that sentence.

4.1 Available to sell

Online availability is never inventory.quantity. It is that quantity minus every live hold. Any shop query reading the raw quantity is a defect. 

-- Available-to-sell for one variant at one branch.
-- Expiry is evaluated in the query, so correctness never
-- depends on a sweeper job having run.
SELECT i.quantity - COALESCE(r.held, 0) AS ats
FROM inventory i
LEFT JOIN (
  SELECT variant_id, branch_id, SUM(quantity) AS held
  FROM stock_reservations
  WHERE status = 'held' AND expires_at > now()
  GROUP BY variant_id, branch_id
) r ON r.variant_id = i.variant_id AND r.branch_id = i.branch_id
WHERE i.variant_id = $1 AND i.branch_id = $2;

4.2 Taking a hold

Add-to-cart is the moment stock is committed. The inventory row is locked first, which serialises every concurrent attempt on that variant and makes the check-then-insert safe without relying on a transaction isolation level. 

BEGIN;

-- Serialise all contenders for this piece.
SELECT quantity FROM inventory
 WHERE variant_id = $1 AND branch_id = $2
 FOR UPDATE;

-- Recompute ATS under the lock. If it cannot cover the
-- request, roll back and return 409 SOLD_OUT.

INSERT INTO stock_reservations
  (variant_id, branch_id, quantity, cart_id, status, expires_at)
VALUES ($1, $2, $3, $4, 'held', now() + interval '15 minutes');

COMMIT;

4.3 Reservation lifecycle

Expiry is lazy: the availability query filters on expires_at > now(), so an expired hold stops blocking a sale the instant it lapses, with no scheduled job in the loop. A periodic sweeper exists only to flip stale rows to expired for tidiness and reporting — if it never runs, the system is still correct. On a 1 GB box that distinction matters.

4.4 The other side: the shop floor

A hold is invisible to the customer standing at the counter, so the cashier needs to see it. Scanning a barcode with a live web hold shows a warning — not a block:

  • Unpaid web hold, cashier scans it. Warning banner: "1 unit held online until 14:32." The cashier may sell it. The customer in the shop is real and present; the web shopper has not paid.
  • Paid web order, cashier scans it. Hard block, owner-PIN override only when stock cannot cover both. That garment is owed to someone who has already paid for it.

4.5 When the piece vanishes after payment

The window between a shopper paying and the webhook confirming is small but not zero, and a counter sale can land inside it. The confirmation transaction therefore re-checks raw on-hand stock, and failing that check is an expected outcome with a defined path, not an error:

  1. Webhook

    Cashfree confirms payment. Signature verified against the raw body, exactly as the existing POS webhook does.

  2. Backend

    Open a transaction. Re-check inventory.quantity for every line, ignoring the order's own hold.

  3. Backend

    If every line is covered: create the Sale, decrement stock, mark reservations consumed, move the order to paid.

  4. Backend

    If any line is short: the order becomes failed, an automatic refund is issued, and no Sale is ever written.

  5. Customer

    WhatsApp message — either the order confirmation, or an apology naming the piece that sold, with the refund reference.

4.6 Race matrix

Shopper pays, webhook never arrives Reconciliation poll against the gateway Order settles late, or refunds after the hold lapses

5Order & payment flow

  1. Storefront

    Shopper adds a piece. The backend takes a 15-minute hold and returns the cart with a countdown.

  2. Storefront

    Checkout begins. Login by phone OTP over WhatsApp; the account is matched to an existing Customer by phone so the CRM record is never duplicated.

  3. Backend

    Quote: offers re-evaluated through the existing engine (online-eligible only), loyalty redemption applied, shipping added, GST resolved. Holds extended to 20 minutes.

  4. Backend

    ShopOrder written as pending_payment. A Cashfree intent is created — through a session-free path, since there is no cashier and no open till.

  5. Gateway

    Shopper pays. The webhook arrives on the existing raw-body verified endpoint.

  6. Backend

    Stock re-checked (§4.5). On success: Sale(channel: 'online') created via the shared checkout core, bill numbered O-0001, loyalty accrued, holds consumed.

  7. ERP

    The order appears on the fulfilment screen. Staff pick, pack, print the slip through the existing printing module, enter the AWB and ship.

  8. Customer

    WhatsApp at each transition: confirmed, shipped with tracking, delivered.

Reuse, not reimplementation

Step 6 calls the same checkout() the till calls. It already accepts channel: 'online' and a clientRef idempotency key. What the online path needs is not new checkout logic but the four guards in §6.

6Guard rails on the POS

Primary hazard

pos/service.ts contains topUpShortfall(), which silently manufactures an adjustment stock-in whenever a scan exceeds recorded stock, so that a counter sale never dead-ends. For a cashier holding the garment that is exactly right — the piece plainly exists, the records were wrong.

Reached from the web it is the worst possible behaviour: it would invent stock for a garment that has already been sold, accept the money, and leave nothing to ship. The online path must fail loudly instead.

GuardWhereBehaviour on the online path
No shortfall top-uppos/service.ts → _checkoutTxncritical Throw INSUFFICIENT_STOCK; never adjust stock upward
No open till requiredshop/payment intentSkip the PosSession check that createUpiPayment() enforces
System actorSale.userIdSale.userId is non-null; online sales are attributed to a seeded "Online Store" user
No commissioncommission calculationNo agent served the sale, so no commission row is written
Online bill prefixBillSequenceSeparate sequence — O-0001, never interleaved with counter bills
Drawer untouchedcloseSessionExpected-cash math must exclude online sales entirely — to be verified, not assumed
Scan of a paid piecepos lookupBarcodeHard block with owner-PIN override when an unfulfilled paid order claims it

Each guard gets a regression test that fails if the guard is removed. These are the places where a future refactor could quietly reintroduce double-selling, and a comment is not sufficient protection.

A sold-out item's URL must not 404 — it returns 200 with an out-of-stock state and links to similar products, which preserves accumulated search equity instead of discarding it whenever a size runs out.

Images

The schema has no image concept at all today, so every product needs shots before it can be listed — a content operation that will outlast the code. Buying in depth helps sharply: one shoot covers a product and every size variant inherits it. Images are served from object storage behind a CDN, never from the application box. Launch curated rather than exhaustive.

9Deployment

The whole ERP currently runs on one free Oracle ARM VM with Node capped at a 1 GB heap, nginx in front, and the Angular build served out of backend/public. Adding a public, image-heavy, crawler-visible Next.js app to that box is the main operational risk in this project.

  • The storefront runs as a second systemd unit on :3001. It is not merged into the Express process — a memory spike from a crawler must not be able to take the till offline.
  • nginx routes by hostname: shop. → 3001, erp. → 3000.
  • deploy/deploy.sh gains a storefront build step and a second systemctl restart.
  • Images never touch the box. Object storage plus CDN from day one.
  • Budget for moving off the free tier once real traffic and crawlers arrive. Plan the migration rather than discovering it during a sale.

10Test plan

The correctness of this system is almost entirely about concurrency, so the tests that matter are the ones that are awkward to write. Each row of the §4.6 race matrix becomes an integration test against a real Postgres, not a mocked client — the locking behaviour is the thing under test.

  • Parallel add-to-cart on a variant with one unit left: exactly one hold is granted.
  • Counter sale during a live web hold: the payment refunds, no Sale row is written, no stock goes negative.
  • Guard test: an online checkout short of stock throws, and topUpShortfall is never reached. This test failing means someone has reintroduced double-selling.
  • Duplicate webhook delivery produces one sale, via the existing clientRef path.
  • Expired hold releases stock with the sweeper deliberately disabled — proving lazy expiry stands alone.
  • Online sale leaves drawer expectation, commission and daily rollups untouched.
  • Counter-only offers do not appear in an online quote.
